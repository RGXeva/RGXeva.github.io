Distributed EV Charging Network Simulation

Two-person course project · Lead, about 90% of the work · Sep – Oct 2026 · Code github.com/RGXeva/ev-charging-simCOpen MPIOpenMPSLURMPython

A grid of charging stations simulated as a distributed sensor network. A congested station asks its neighbours first; only when they are full too does it ask the base station for the nearest free one.

WHAT I BUILT

  • Compared 8 network topologies and chose a 2-D grid: one MPI process per station, with neighbours found through a Cartesian topology
  • One OpenMP thread per charging port, each writing only its own slot: no locks and no data races
  • Designed a non-blocking, on-demand neighbour protocol; persistent receives answer neighbours at any time, so it cannot deadlock
  • The base station checks neighbour reports within a time window, then searches Manhattan rings outwards and returns every free station at the nearest distance
  • Graceful shutdown: the base broadcasts TERMINATE, nodes finish open work and exit together, then free threads, communicators and memory
  • Owned the architecture, about 1,500 lines of C, cluster experiments, slides and the presentation

Parallel prime search: find the bottleneck, then fix it

Two-person course project · Lead, about 90% of the work · Aug – Sep 2026CMPIOpenMPPthreadsSLURM
Speed-up versus number of workers
Median cluster runs against the serial version; dashed line: Amdahl model from the measured serial fraction

Starting from a serial version, I built Pthreads, OpenMP, MPI and hybrid MPI+OpenMP versions, measuring before every optimisation.

Bottleneck 1: load imbalance
Larger numbers need more trial divisions, so contiguous blocks overloaded the last process. Dealing blocks of 4,096 numbers round-robin moved the slowest-to-mean ratio 1.41 → 1.00 and 16-process speed-up 11.4× → 15.6×.
Bottleneck 2: serial output on rank 0
A pilot run showed all output formatting piled on rank 0. Having each rank format its own primes, with rank 0 only writing the file, moved pilot speed-up 12.2× → 15.1×.

GPU image rotation

Two-person course project · Oct 2026CUDANumbaPython

Rotating images on the GPU: one thread per output pixel, each inverse-mapping back to the source image and writing only its own pixel, so no atomics are needed.

  • 16 × 16 thread blocks with a ceiling-divided grid; threads past the edge exit at a bounds check
  • Timing covers the whole copy-in, kernel and copy-out pipeline, compared against a compiled CPU version
  • Every run is checked against the CPU result; all trials match
  • The larger the image, the smaller the share of data transfer and the bigger the GPU’s lead
